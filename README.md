## 3DAndEngine — Core
3DAndEngine core — это высокопроизводительное, минималистичное и отказоустойчивое инфраструктурное ядро для модульного 3D-движка, написанное на C++17/20.
Ядро предоставляет исключительно базовые системные сервисы: управление жизненным циклом, декларативное внедрение зависимостей, потокобезопасную шину событий и асинхронный планировщик задач. Весь прикладной функционал движка (рендеринг, физика, звук, логика) выносится во внешние динамически загружаемые библиотеки (DLL / SO / DYLIB).
------------------------------
## 🎯 Архитектурные принципы

   1. Максимальная изоляция (Clean Architecture): Ядро полностью инкапсулировано и не содержит зависимостей от графических API (Vulkan/OpenGL) или физических движков.
   2. Легковесный плагинный слой (Plain C Export): Отказ от жестких C++ интерфейсов и сложных JSON-манифестов совместимости внутри плагинов. Сторонние модули могут создаваться изолированно и требуют лишь экспорта одной стандартной инициализирующей C-функции.
   3. Строгая фазированность: Запуск и остановка подсистем происходят не хаотично, а через предсказуемые глобальные точки синхронизации (двунаправленный жизненный цикл).
   4. Потоковая безопасность (Thread-Safety): Все ключевые подсистемы ядра (EventBus, TaskScheduler, ServiceManager) спроектированы для работы в многопоточной среде и защищены от data race и дедлоков.

## 📐 Подробный разбор компонентов ядра## 1. Application (Сердце системы)
Класс-координатор, управляющий главным циклом приложения и последовательностью инициализации инфраструктуры.

* Логика работы:
1. В конструкторе гарантированно аллоцирует потокобезопасную шину событий EventBus, предотвращая nullptr-краши в плагинах.
   2. Регистрирует и синхронно запускает ConfigService для чтения файла конфигурации config.json.
   3. На основе считанных флагов конфига опционально регистрирует LoggerService и TaskScheduler.
   4. Запускает трехфазный цикл инициализации всех зарегистрированных сервисов.
   5. Передает управление LibraryLoader для динамического сканирования и линковки внешних модулей.
   6. Входит в главный симуляционный цикл (Main Loop), генерируя системные события (например, "tick").
   7. При выходе выполняет Graceful Shutdown в строго обратном порядке.

## 2. ServiceManager (Сервис-локатор и DI)
Контейнер, осуществляющий декларативное управление зависимостями подсистем с помощью Variadic Templates. Хранение сервисов унифицировано на базе std::shared_ptr<IService>, что исключает Undefined Behavior при приведении типов.

* Публичный интерфейс:

template<typename T, typename... Deps> void registerService(std::shared_ptr<T> svc);template<typename T> std::shared_ptr<T> getService();void startAll();void stopAll();

* Алгоритм разрешения зависимостей (Топологическая сортировка):
Метод startAll() строит направленный граф зависимостей подсистем. С помощью обхода в глубину (DFS) вычисляется строго линейный порядок выполнения.
* Защита от циклов: Алгоритм отслеживает состояния узлов графа (0 - unvisited, 1 - visiting, 2 - visited). Если в процессе обхода узел переходит в состояние 1 повторно, выбрасывается std::runtime_error с текстовой визуализацией циклического пути (например, SvcA -> SvcB -> SvcA).
* Трехфазный жизненный цикл (IService):
Запуск происходит строго в прямом топологическом порядке (от независимых к зависимым подсистемам) по следующим фазам:
1. init(ServiceManager&): Настройка параметров, чтение индивидуальных конфигураций. Если сервис возвращает false, инициализация ядра прерывается.
   2. start(): Аллокация тяжелых ресурсов, запуск внутренних рабочих потоков подсистемы.
   3. postStart(): Точка синхронизации. Вызывается, когда абсолютно все сервисы запущены и готовы безопасно вызывать методы друг друга.
* LIFO Остановка: Метод stopAll() останавливает сервисы в строго обратном порядке от вычисленного топологического. Зависимые модули тушатся первыми, а базовые утилиты (например, логгер) закрываются последними, исключая падения на этапе деаллокации.

## 3. TaskScheduler (Пул потоков)
Многопоточный асинхронный планировщик задач, использующий примитивы синхронизации C++ стандартной библиотеки. Количеством потоков по умолчанию управляет операционная система (std::thread::hardware_concurrency()).

* Публичный интерфейс:

template<typename F, typename... Args> auto submit(F&& f, Args&&... args) -> std::future<typename std::invoke_result_t<F, Args...>>;void enqueue(std::function<void()> fn);

* МеханизмGraceful Shutdown (Защита от дедлоков):
В старой реализации пул зависал, если задачи оставались в очереди на момент закрытия. В текущей реализации метод stop() атомарно:
1. Захватывает мьютекс и выставляет флаг запрета приема задач accepting_ = false.
   2. Полностью очищает очередь tasks_ от невыполненных задач.
   3. Вызывает cv_.notify_all(), пробуждая спящие потоки.
   4. Потоки заходят в предикат cv_.wait, видят, что задач нет, а accepting_ равен false, и чисто выходят из бесконечного цикла workerLoop.
   5. Основной поток безопасно дожидается завершения каждого воркера через t.join().

## 4. EventBus (Шина событий)
Обеспечивает слабосвязанную архитектуру обмена сообщениями в реальном времени между ядром, сервисами и внешними DLL модулями.

* Публичный интерфейс:

EventHandlerId subscribe(const std::string &topic, std::function<void()> handler);void unsubscribe(const std::string &topic, EventHandlerId id);void publish(const std::string &topic);

* Защита от взаимной блокировки (Deadlock Prevention):
Метод publish спроектирован так, что критическая секция (std::lock_guard) удерживается минимальное время — только на момент копирования массива зарегистрированных колбэков в локальный буфер. Сами вызовы функций-обработчиков происходят уже вне мьютекса. Это позволяет разработчикам безопасно вызывать методы subscribe или unsubscribe прямо внутри обработчика события, полностью исключая рекурсивный дедлок.

## 5. LibraryLoader (Динамический линкер модулей)
Кроссплатформенный загрузчик бинарников из физической памяти в виртуальное адресное пространство процесса движка.

* Платформенная изоляция: Под капотом инкапсулированы системные вызовы Win32 API (LoadLibraryA, GetProcAddress, FreeLibrary) и POSIX стандарты (dlopen, dlsym, dlclose).
* Логика работы:
1. discoverAndLoad рекурсивно ищет файлы с расширениями .dll (Windows), .so (Linux) или .dylib (macOS).
   2. Загрузка происходит атомарно в один этап через loadLibrary(), предотвращая двойные дисковые операции чтения. Хендл сразу фиксируется в векторе.
   3. initializeAll осуществляет поиск экспортируемого символа "InitializeModule". Если он найден, управление передается коду внешней библиотеки с внедрением ссылки на ServiceManager.

## 📦 Спецификация внешнего модуля (DLL)
Чтобы написать плагин для движка, разработчику не нужно наследоваться от внутренних классов ядра и настраивать сложную конфигурацию сборки. Достаточно скомпилировать динамическую библиотеку с экспортом одной глобальной C-функции.

#include "core/ServiceManager.h"#include "core/LoggerService.h"
// extern "C" отключает манглинг имен компилятора C++, делая символ видимым для dlsym/GetProcAddressextern "C" {
    #if defined(_WIN32)
        __declspec(dllexport) void InitializeModule(core::ServiceManager& services) {
    #else
        void InitializeModule(core::ServiceManager& services) {
    #endif
        // Перехватываем управление и запрашиваем системный логгер ядра движка
        auto lg = services.getService<core::LoggerService>();
        if (lg) {
            lg->info("[Module] Successfully linked into 3DAndEngine process memory!");
        }
    }
}

## ⚙️ Файл конфигурации (config.json)
Файл должен лежать в корневом каталоге выполнения приложения (рядом с исполняемым файлом движка).

{
  "core": {
    "enable_logger": true,
    "enable_scheduler": true,
    "enable_plugin_discovery": true
  },
  "plugin_paths": [
    "plugins"
  ]
}

## 🔨 Сборка, тестирование и CI/CD## Локальная сборка (Рекомендуется через vcpkg)
Проект использует современные стандарты CMake мишени (CMake Targets) и легко подхватывает зависимости через пакетный менеджер.

# 1. Генерация конфигурации сборки с тулчейном vcpkg и тестами
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE="C:\path\to\vcpkg\scripts\buildsystems\vcpkg.cmake" -DBUILD_TESTS=ON
# 2. Компиляция всего проекта в режиме отладки (Debug)
cmake --build build --config Debug
# 3. Запуск встроенных модульных тестов графа и пула потоков
ctest --test-dir build --output-on-failure -C Debug

## Автоматизация CI/CD (GitHub Actions)
В репозиторий интегрирован готовый пайплайн автоматизации .github/workflows/ci.yml:

* События триггера: Каждый push или pull_request в ветки main/master, а также публикация официального релиза (release).
* Матрица сборки: Параллельно разворачиваются три независимых агента на чистых ОС: windows-latest, ubuntu-latest, macos-latest.
* Кэширование: Реализовано продвинутое многоуровневое кэширование бинарных архивов vcpkg и промежуточных файлов сборки CMake, что сокращает время CI с 15 минут до 40 секунд при повторных прогонах.
* Авто-Релиз: При публикации нового тега на GitHub экшен автоматически компилирует оптимизированную Release-версию движка, упаковывает её в кроссплатформенный .zip архив (включая все необходимые скомпилированные .dll/.so модули) и прикрепляет архивы к релизу с помощью современного инструмента softprops/action-gh-release@v2.
